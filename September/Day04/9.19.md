## 二、今天理清的核心概念

### 1. Agent 是什么

> **让大模型自己决定"下一步做什么"的系统。**

四要素：**大脑（LLM）+ 工具（Tools）+ 记忆（Memory）+ 规划（Planning）**

运行循环：`思考 → 行动（调工具）→ 观察（看结果）→ 再思考 → 直到完成`

**判断是不是 Agent 的唯一标准**：模型能不能自主决定"要不要调工具、调哪个、还要不要再调一次"？能 → Agent；不能 → 只是 Chain。

### 2. Agent 和 LangChain 的区别（不是同类，不能对比）

| | Agent | LangChain |
|---|---|---|
| 是什么 | 一种**应用形态** | 一个**开发框架** |
| 类比 | 一道菜 | 厨房和厨具 |
| 关系 | 目的 | 手段 |

**可以用 LangChain 做 Agent，也可以不用**（昨天原生 SDK 手撸的就是）。

### 3. Function Calling 的作用

让模型从"只会说"变成"能做事"——补上 LLM 的四个短板：

| 短板 | 怎么补 |
|---|---|
| 知识过时 | 调搜索/实时接口 |
| 会编造（幻觉） | 调数据库/向量库拿真实依据 |
| 不能产生动作 | 调发邮件、下单接口 |
| 输出格式不稳 | JSON Schema 约束参数 |

### 4. RAG 的真实机制（纠正一个误解）

**不是"让 LLM 先读一遍文档"**——LLM 从未读过完整文档。

```
完整文档（1000 页）
    ↓ 向量检索（代码执行）
相关片段（3 段）
    ↓ 只把这 3 段塞给 LLM
有依据的回答
```

全量塞进去叫**长上下文**，不叫 RAG。RAG 的精髓是**先检索、只给相关的**。

### 5. Function Calling 和 RAG 的关系

- **Function Calling 是"手"，RAG 是"用这只手翻资料"**
- 工具去查文档/知识库 → 是 RAG
- 工具去查天气、发邮件 → 不是 RAG

用 Agent 方式实现的 RAG 叫 **Agentic RAG**（模型自己决定要不要检索），比传统固定流程的 RAG 灵活。

### 6. MCP 是什么

> **Model Context Protocol = AI 应用的 USB-C 接口**

由 Anthropic 提出，标准化模型与外部工具/数据的连接。

**Server 提供三类东西**：
- **Tools**（工具，模型可调用）
- **Resources**（资源，模型可读取）
- **Prompts**（提示模板）

**与 Function Calling 不冲突**：FC 是"模型怎么表达调用意图"，MCP 是"工具怎么被发现和接入"。

### 7. JSON Schema

> 用 JSON 描述"另一份 JSON 长什么样"的规范。

核心关键字：`type` / `properties` / `required` / **`description`** / `enum` / `items`

`@tool` 装饰器会自动从 Python 类型注解生成 JSON Schema：

| Python | JSON Schema |
|---|---|
| `str` | `"string"` |
| `int` | `"integer"` |
| `float` | `"number"` |
| `list` | `"array"` |
| `dict` | `"object"` |

### 8. SDK 复习

SDK = 封装好的代码包，帮你省掉拼 URL、鉴权、错误处理、JSON 解析等 7 件事。

**探索陌生 SDK 的四招**：`dir()` 看有什么 → `help()` 看用法 → `model_dump_json()` 看结构 → `Ctrl+点击` 看源码

## 三、MCP 两种通信模式对比

| | **stdio** | **streamable-http** |
|---|---|---|
| 怎么工作 | 客户端**启动** server 子进程 | server **独立运行**，客户端连过去 |
| 要不要手动启 server | ❌ 不需要 | ✅ **需要**（先跑起来并保持） |
| 返回值个数 | **2 个** `(read, write)` | **3 个** `(read, write, get_session_id)` |
| 适用场景 | 本地工具（Claude Desktop 那种） | 远程服务、多客户端共享 |
| 坑 | server 里不能 `print()`（污染通信流） | 端口/路径要对应 |

**server 启动方式**：
```python
mcp.run(transport="stdio")                                    # stdio
mcp.run(transport="streamable-http", host="127.0.0.1", port=8000)   # HTTP
```

## 四、今天的踩坑记录（8 个）

| # | 报错 | 原因 | 解决 |
|---|---|---|---|
| 1 | `api_key must be set` | 新文件忘了 `load_dotenv()` | 加 load_dotenv + 显式传 key |
| 2 | `from json import tool` | 导错模块（自动导入误加） | `from langchain.tools import tool` |
| 3 | `KeyError: 0` | `stream()` 返回**字典**不是列表 | 用 `stream_mode="messages"` |
| 4 | `SyntaxError: forgot a comma` | `command=...` 后面缺逗号 | 补逗号 |
| 5 | `stdio_client() missing argument` | 没传 `server_params` | 传参 |
| 6 | `McpError: Connection closed` | server 文件名写错（`04_mcp_...` 实际是 `mcp_...`） | 用**绝对路径** |
| 7 | `method object can't be awaited` | `list_tools` 少了括号 | `list_tools()` |
| 8 | `too many values to unpack` | `streamable_http_client` 返回 **3 个**值 | `(read, write, _)` |

**规律总结**：
- 忘了加括号 → 拿到方法本身（第 7 个 + 昨天的两次）
- 名字/路径写错 → 连接类报错
- SDK 版本差异 → 参数个数变化（stdio 2 个 / http 3 个）

## 五、今天的实用配置

### VS Code 自动导入

设置 JSON 里加：

```json
{
  "python.analysis.autoImportCompletions": true,
  "[python]": {
    "editor.codeActionsOnSave": {
      "source.addMissingImports": "explicit",
      "source.organizeImports": "explicit"
    }
  }
}
```

**前提**：选对解释器（`Ctrl+Shift+P` → Python: Select Interpreter → 选 `.venv`）

**最常用的快捷键**：`Ctrl + .` 在报错的名字上 → 自动补 import
